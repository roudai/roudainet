# Feature Specification: サイト基盤

**Feature Branch**: `001-site-foundation`

**Created**: 2026-10-30

**Status**: Draft

**Input**: User description: "roudai.net を Nuxt 2 から最新の安定版 Nuxt + TypeScript(静的生成のみ)へ再構築する、その最初の機能として「サイト基盤」を作る。対象は共通レイアウト、ナビゲーション、フッター、トップページの骨組み、GitHub Pages へのデプロイ基盤、CI 品質ゲートである。解法ページ本体は別の Spec で扱う。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全ページ共通のヘッダーとフッターで移動できる (Priority: P1)

訪問者は、サイトのどのページを開いても、同じヘッダー(サイト名リンク、各カテゴリのドロップダウンメニュー、GitHub リンク)と同じフッターを見ることができる。ヘッダーのメニューから、目的のカテゴリのページへ移動できる。

**Why this priority**: 基盤の中心となる機能であり、後続の Spec(各解法ページの移植)がすべてこの共通レイアウトの上に載る。これだけでも、サイトの骨格として動作を確認できる。

**Independent Test**: トップページを開き、ヘッダーとフッターが表示されること、各カテゴリのメニューが現行サイトと同じ項目と順序で並ぶことを確認する。

**Acceptance Scenarios**:

1. **Given** 訪問者がトップページを開いている、**When** ヘッダーを見る、**Then** サイト名リンク、F2L / OLL / PLL / BLD / Megaminx / FMC / Clock / Other / Tooks の各メニュー、GitHub リンクが現行サイトと同じ並びで表示される。
2. **Given** 訪問者がデスクトップ幅で閲覧している、**When** カテゴリのメニューにポインターを重ねる、**Then** そのカテゴリのドロップダウンが開き、現行サイトと同じ項目が並ぶ。
3. **Given** 訪問者が任意のページを開いている、**When** ページ下部までスクロールする、**Then** 現行サイトと同じ内容のフッターが表示される。
4. **Given** 訪問者がメニューの外部リンク(competition.roudai.net、blog.roudai.net、各ツールのサイトなど)を選ぶ、**When** リンクを開く、**Then** 現行サイトと同じ外部の URL へ移動する。

---

### User Story 2 - モバイルでメニューを開閉できる (Priority: P2)

モバイルなどの狭い画面で閲覧する訪問者は、バーガーボタンを押してメニューを開閉できる。メニューの項目とリンク先は、デスクトップと同じである。

**Why this priority**: 現行サイトはモバイルでの閲覧に対応しており、パリティ(原則 IV)の対象である。ただし、US1 のレイアウトがあって初めて意味を持つため P2 とする。

**Independent Test**: 狭い画面幅でトップページを開き、バーガーボタンでメニューが開閉することと、開いたメニューから各カテゴリの項目を選べることを確認する。

**Acceptance Scenarios**:

1. **Given** 訪問者が狭い画面で閲覧している、**When** ページを開く、**Then** メニューは閉じた状態で、バーガーボタンが表示される。
2. **Given** メニューが閉じている、**When** バーガーボタンを押す、**Then** メニューが開き、全カテゴリの項目が選べる。
3. **Given** メニューが開いている、**When** バーガーボタンをもう一度押す、**Then** メニューが閉じる。

---

### User Story 3 - 運営者が安全に変更を統合し、公開できる (Priority: P2)

運営者は、機能ごとの作業ブランチを統合ブランチ(`nuxt4-rebuild`)へ PR でマージして、移植を進められる。PR では Lint、型チェック、静的生成のビルド確認が自動で実行され、結果が分かる。これらに失敗した変更はマージできない。本番への公開は `main` へのマージ時だけ自動で行われ、PR やブランチへの push では公開されない。

**Why this priority**: 以降の移植の各 Spec が、この品質ゲートの上で進む。また、公開の経路をここで決めておかないと、移行途中の状態を誤って本番へ出すおそれがある。

**Independent Test**: 統合ブランチ宛ての PR を作り、Lint、型チェック、ビルド確認が自動で実行されること、失敗する変更ではマージが止まること、公開が行われないことを確認する。

**Acceptance Scenarios**:

1. **Given** `main` または `nuxt4-rebuild` 宛ての PR が作られた、**When** PR の確認が実行される、**Then** Lint、型チェック、静的生成のビルドが実行され、その結果が PR 上で確認できる。
2. **Given** Lint または型チェックが失敗する変更がある、**When** PR をマージしようとする、**Then** マージできない。
3. **Given** PR またはブランチへの push が行われた、**When** 確認が完了する、**Then** 本番サイトは更新されない。
4. **Given** 変更が `main` へマージされた、**When** 公開の処理が実行される、**Then** 生成されたサイトが `https://roudai.net` へ公開される。
5. **Given** 全移植と切り替えチェックリストが完了していない、**When** 運営者が公開の可否を判断する、**Then** `main` へのマージは行わない運用であることが、リポジトリの文書から分かる。

---

### User Story 4 - 公開物に必要なファイルが含まれ、広告が含まれない (Priority: P3)

運営者が公開したサイトでは、独自ドメインを維持するためのファイル(`CNAME`)と、アプリの広告配信元を検証するためのファイル(`app-ads.txt`)が、サイトのルートに存在する。一方、Web サイトには Google 広告の表示や、そのためのファイル(`ads.txt`)が含まれない。

**Why this priority**: 公開時に必須の条件だが、レイアウトや CI が先に整ってから確認できる。切り替え時のチェックリスト項目でもある。

**Independent Test**: 静的生成の出力を調べ、`CNAME` と `app-ads.txt` が存在し、`app-ads.txt` の内容が移植元と同一であること、`ads.txt` と広告関連のスクリプトや要素が存在しないことを確認する。

**Acceptance Scenarios**:

1. **Given** サイトを静的生成した、**When** 出力のルートを確認する、**Then** `CNAME`(内容は `roudai.net`)と `app-ads.txt` が存在する。
2. **Given** 生成した `app-ads.txt`、**When** 移植元(`legacy/pages/app-ads.txt`)と比較する、**Then** 内容が完全に一致する。
3. **Given** 生成したサイト、**When** `/ads.txt` を要求する、**Then** 存在しない(404)。
4. **Given** 生成したサイトの任意のページ、**When** ページの内容を確認する、**Then** Google 広告のスクリプト、広告枠、広告用の meta タグが含まれない。

---

### User Story 5 - トップページの骨組みを確認できる (Priority: P3)

訪問者がトップページ(`/`)を開くと、共通のヘッダーとフッターに挟まれた、トップページの骨組みが表示される。トップページの中身(現行のコンテンツの移植)は、後続の Spec で行う。

**Why this priority**: 共通レイアウトの動作確認と、デプロイ経路の確認に使う最小のページである。内容の移植は範囲外のため、優先度は低い。

**Independent Test**: `/` を開き、エラーなく表示され、ヘッダーとフッターが含まれることを確認する。

**Acceptance Scenarios**:

1. **Given** 訪問者が `/` を開く、**When** ページが表示される、**Then** エラーなく表示され、共通のヘッダーとフッターが含まれる。

---

### Edge Cases

- 未移植のページへのメニューリンクを選んだ場合: この Spec ではメニュー構成だけを先に作るため、リンク先が存在せず 404 になる。`main` へマージするまでは本番に公開されないため許容し、全移植の完了までに、現行の全パスに到達できることを切り替えチェックリストで確認する。
- メニューを開いたまま画面幅が変わった場合: デスクトップ幅では常時表示のメニューに、狭い幅ではバーガーボタンの表示に切り替わり、メニューが操作不能にならない。
- ドロップダウンをキーボードやタッチ操作で開く場合: ポインターを重ねる操作がなくても、メニューの項目を選べる。
- PR の確認が失敗した場合: どの工程(Lint、型チェック、ビルド)が失敗したかを、PR 上で判別できる。
- 公開の処理が失敗した場合: 直前に公開されていたサイトがそのまま残り、壊れた状態のサイトは公開されない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: サイトは、すべてのページで共通のヘッダーとフッターを表示しなければならない(MUST)。
- **FR-002**: ヘッダーは、サイト名リンク、F2L / OLL / PLL / BLD / Megaminx / FMC / Clock / Other / Tooks のドロップダウンメニュー、GitHub リンクを、現行サイトと同じ項目と順序で含まなければならない(MUST)。
- **FR-003**: メニューの各項目のリンク先は、現行サイト(`legacy/components/NavBar.vue`)と同じパスまたは同じ外部 URL でなければならない(MUST)。
- **FR-004**: 狭い画面では、メニューはバーガーボタンで開閉でき、デスクトップ幅と同じ項目を含まなければならない(MUST)。
- **FR-005**: ヘッダーとフッターの見た目(色、余白、メニューの挙動)は、現行サイトと同等でなければならない(MUST)。デザインの刷新を行ってはならない(MUST NOT)。
- **FR-006**: トップページ(`/`)は、共通レイアウトを含む骨組みとして表示されなければならない(MUST)。現行のコンテンツの移植は、この Spec の対象外とする。
- **FR-007**: 解法ページ本体(pll、oll、f2l、bld、fmc、megaminx、clock、other)の移植は、この Spec の対象外とする。メニューのリンク先は、これらのページが後続の Spec で作られる前提で、現行と同じパスを指さなければならない(MUST)。
- **FR-008**: サイトは、最新の安定版の Nuxt と TypeScript で構築し、静的生成のみで出力しなければならない(MUST)。サーバーの実行環境を必要としてはならない(MUST NOT)。
- **FR-009**: `main` または `nuxt4-rebuild` 宛ての PR では、Lint、型チェック、静的生成のビルド確認が自動で実行されなければならない(MUST)。この確認は、本番へ公開してはならない(MUST NOT)。
- **FR-010**: Lint または型チェックに失敗した変更は、マージできてはならない(MUST NOT)。マージを止める手段は、リポジトリの設定で運営者が構成する。
- **FR-011**: 本番への公開は、`main` へのマージ時にだけ自動で実行されなければならない(MUST)。公開先は `https://roudai.net` とする。
- **FR-012**: 全移植と切り替えチェックリストが完了するまで `main` へマージしない運用と、`nuxt4-rebuild` を統合ブランチとして使う運用を、リポジトリの文書に記載しなければならない(MUST)。
- **FR-013**: 生成したサイトのルートには、`CNAME`(内容は `roudai.net`)と、内容を変更していない `app-ads.txt` が含まれなければならない(MUST)。
- **FR-014**: 生成したサイトには、`ads.txt`、Google AdSense のスクリプトや広告枠、広告用の meta タグ、広告表示を前提にしたレイアウトの余白を含めてはならない(MUST NOT)。
- **FR-015**: パッケージマネージャーとロックファイルは、それぞれ1つに統一しなければならない(MUST)。`yarn.lock` と `package-lock.json` を併存させてはならない(MUST NOT)。
- **FR-016**: `legacy/` 配下のファイルを変更してはならない(MUST NOT)。参照用にのみ使う。

### Key Entities *(include if feature involves data)*

- **メニュー構成**: ヘッダーに表示するカテゴリ(F2L、OLL、PLL、BLD、Megaminx、FMC、Clock、Other、Tooks)と、各カテゴリに属する項目(表示名、リンク先)の並び。リンク先は、サイト内のパスか外部の URL のどちらかである。
- **公開物のルートファイル**: 生成したサイトのルートに置く `CNAME` と `app-ads.txt`。独自ドメインの維持と、アプリの広告配信元の検証に使う。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 現行のメニュー項目(表示名とリンク先)のすべてが、新サイトのメニューに同じ順序で存在し、不足や相違が0件である。
- **SC-002**: 訪問者は、トップページからヘッダーのメニュー経由で、現行サイトと同じパスのリンクを2操作以内(メニューを開く、項目を選ぶ)で選べる。
- **SC-003**: 狭い画面と広い画面の両方で、ヘッダーとフッターを現行サイトと並べて比較したとき、色、余白、メニューの挙動に、運営者が気づく相違がない。
- **SC-004**: `main` または `nuxt4-rebuild` 宛ての PR を作ってから、Lint、型チェック、ビルド確認の結果が出るまでの時間が、15分以内である。
- **SC-005**: PR やブランチへの push では、本番サイトの更新が0回である。
- **SC-006**: 静的生成の出力で、`CNAME` と `app-ads.txt` が存在し、`app-ads.txt` が移植元と完全に一致し、`ads.txt` と広告関連の要素が0件である。
- **SC-007**: Lint、型チェック、静的生成が、クリーンな環境から手順書どおりに実行して、すべて成功する。

## Assumptions

- 訪問者は、モバイルとデスクトップの一般的な最新ブラウザーで閲覧する。
- 現行のヘッダーとフッターの内容(項目、リンク先、見た目)は、`legacy/` にあるソースを正とする。フッターの内容は、Plan の段階で `legacy/components/FooterBar.vue` から確認する。
- 未移植のページへのリンクは、この Spec の時点では 404 になる。`main` へはマージしないため、本番の訪問者には影響しない。現行の全パスへの到達は、切り替えチェックリスト(原則 II)で確認する。
- 技術選定(CSS の手段、Buefy の代替、デプロイの方式など)は、この Spec には含めず、Plan で決める。原則 VIII のとおり、採用前に spike で検証する。
- CI で必要なマージの制限(ブランチ保護)は、リポジトリの設定で運営者が行う。設定そのものはリポジトリの外にある。
- AdSense の管理画面など、リポジトリの外にある広告関連の設定は、この Spec の対象外とする。
- テストコードは、この Spec では必須としない。ただし、Lint と型チェックは必須である(原則 V)。
